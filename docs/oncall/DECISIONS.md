# Decisions

Each entry: what was decided, the evidence, and why. Newest at the bottom.

## D-001 MinIO replaced by SeaweedFS (config only)
- **Evidence:** `docker pull minio/minio:latest` and `minio/mc:latest` -> "pull access denied ... repository does not exist". The project's alternate registry `quay.io/minio/minio:latest` and `quay.io/minio/mc:latest` -> `401 UNAUTHORIZED` (not pullable anonymously). No same-version image exists, so the SPEC "Situation" rule applies.
- **Decision:** `chrislusf/seaweedfs:4.53` (pinned tag) runs `weed mini` with an S3 gateway. To change **only configuration**: the compose service is still named `minio`, still listens on port 9000, and still uses the access key / secret `minioadmin` / `minioadmin` (an `s3.json` identity file in `infra/seaweedfs/`). The bucket `payments-lake` is created on startup by `S3_BUCKET`, replacing the `minio-init` job (the `minio/mc` image is also gone). The Spark `s3a://` endpoint, path-style flag and credentials in the pipeline code did not change at all.
- **Verified:** Delta table init, streaming MERGE, ledger writes, checkpoints and the parity checker all run unchanged against it (see AUDIT.md rows 1-3).
- **Port binding:** published as `127.0.0.1:9000` (this is a new service definition; the SPEC safety rule says new ports bind to loopback). The other pre-existing services keep their original `ports:` mappings.
- The obsolete `version:` key was removed from the compose file (Compose v5 warns on it).
- The Debezium plugin is still installed by `confluent-hub` inside the Connect image at startup (2.5.4); that download works from this box, so no change was needed there.

## D-007 Parity checker oracle
`scripts/parity_checker.py` fails with `ORACLE FAIL` unless the quarantined count is exactly 0 or 53 (the number of Postgres rows the Day-5 injection suite creates). Any other number of DLQ'd rows (for example the demo scenario in this project) makes it exit 1 even when the lake is correct. The existing script is left as is (baseline records its behaviour). The on-call console's drained parity check is a separate implementation that accounts for quarantined keys without the hard-coded 53.

## D-008 Replay publishes to the normal CDC topic, not a `cdc.replay` topic (SPEC fact was wrong)
- **Evidence:** `spark/jobs/payments_cdc_job.py` reads `.option("subscribe", TOPIC)` with `TOPIC = "payments.public.transactions"` only. The SPEC says replay re-publishes to "a replay topic the Spark job already treats like normal input"; no such topic exists and the job does not read one.
- **Decision:** replay-svc re-publishes the record as a Debezium-envelope Avro message on `payments.public.transactions`, built with the repo's own producer helpers (`scripts/inject_bad_records._get_avro_serializer/_envelope/_try_serialize`), carrying the record's ORIGINAL LSN. That is the exact input the job already decodes, validates and MERGEs, so no pipeline logic or subscription changed. A repeat is a no-op by the existing `staged.lsn > target.lsn` guard.

## D-009 replay-svc design choices
- The validator is a Spark DataFrame function (`spark/utils/validator.validate`), so replay-svc evaluates a one-row DataFrame in a small local Spark session instead of copying the rules into Python. The merchant set comes from the pipeline's own `MerchantRegistry`, force-refreshed per call. Cost: a JVM in the replay process (about 8 s to warm up; the gRPC health check reports NOT_SERVING until it is ready) and about a second per replay.
- Proto names follow `buf lint` STANDARD: enum values are `REPLAY_STATUS_*` with `REPLAY_STATUS_UNSPECIFIED = 0`, and `LakeStats` takes a `LakeStatsRequest` (not `google.protobuf.Empty`).
- Added `REPLAY_STATUS_PENDING` (published but the lake does not hold it yet) to the four statuses in the SPEC, because a replay can be accepted by Kafka and not yet visible; the HTTP layer will map it to 202.
- DLQ record id = its offset in the single-partition DLQ topic. "Open" DLQ records are derived, not stored: a record is applied when the lake holds its key at an LSN >= the record's LSN, so a replayed (or later-deleted) record leaves the queue without any extra state to keep consistent. In-page duplicates of the same key+LSN (the DLQ is at-least-once) are collapsed.

## D-010 Bug found by running it: stale merchant cache re-quarantines a replayed record
- **Evidence:** injected a transaction for `MERCH_DEMO_A` (unknown) -> DLQ offset 108. Replay -> `STILL_INVALID UNKNOWN_MERCHANT` (correct). Added the merchant to Postgres and replayed immediately: record published, but the DLQ topic grew from 109 to 110 messages and the lake never got the row (replay-svc waited 75 s, `PENDING`). Cause: the Spark job's `MerchantRegistry` refreshes at most every 120 s (`MERCHANT_REFRESH_SECONDS`), so the streaming validator still did not know the merchant. After the cache aged out, the same replay returned `APPLIED` and a second one `ALREADY_APPLIED`.
- **Not changed:** the validator and its cache are pipeline rules, so they stay. replay-svc instead detects a new DLQ message for the same key+LSN while it waits and answers `PENDING` immediately with the reason ("quarantined it again ... cache refreshes every 120 s; retry"). The demo and the replay test wait for the cache before replaying.

## D-011 Consumer lag: progress events carry exact end offsets (Pushgateway is only a fallback)
- **Evidence (found running the Go collector against the live stack):** Spark Structured Streaming commits no consumer group, so `kadm` can only list END offsets. The only "processed offset" series in the repo is `payments_cdc_processed_offset` on the Pushgateway, and while idle it was permanently one batch stale: Kafka end offset for partition 2 was 2354, the Pushgateway said 2353, so the console showed `lag_total = 1` forever and a drained check could never become true (`curl localhost:9091/metrics | grep processed_offset` vs `GetOffsetShell --time -1`). Cause: the driver pushes `lastProgress` from the previous batch, and empty batches never push (README "Honest Limitations" #1).
- **Decision:** the `pipeline.progress` event (observability only, still after the ledger commit) also carries `end_offsets` = exclusive end offset per partition. They are computed from the RAW Kafka batch (`foreach_batch_wrapper` hands the raw DataFrame to `_emit_progress` through a module-level side channel), not from the deserialized rows, because the deserializer drops Kafka tombstones (null values) and a trailing tombstone would otherwise leave a permanent phantom lag of 1. Go takes the max per partition from events, and falls back to the Pushgateway only for partitions no event has mentioned yet.
- Existing tests, the parity checker and the exactly-once replay check were rerun after this second pipeline-side change: `results/oncall/after_phase2_progress_offsets.json` (23 passed, PARITY: PASS, replay proofs passed).

## D-012 Snapshot semantics (what each number means)
- `events_in_per_sec`: growth of the CDC topic's end offsets over 10 s. `events_out_per_sec`: rows merged by batches observed in the last 30 s divided by 30.
- `freshness_seconds` = now - max committed source time (the SPEC definition) and is shown with `caught_up`. The p50/p95 over 60 s are sampled ONLY while the pipeline is behind (`lag > 0`) and a batch committed in the last 60 s. Reason: when it is caught up and the source is quiet the number just measures how long the source has been quiet; feeding it into the parity allowance (`rate x p95 x 1.5`) would inflate the allowance at the start of the next burst and hide a real mismatch. The freshness alert also requires `!caught_up`.
- Parity badge: `in_sync` if |source - lake - quarantined| <= ceil(rate x p95 x 1.5); `catching_up` above that; `mismatch` only when the stream is **drained** (lag 0, no batch for 15 s, Kafka end offsets unchanged for 15 s, source row count unchanged for 15 s); `unknown` if a needed source is down. Measured: the badge says `catching_up` for the first seconds of a burst (no latency sample yet), `in_sync` while streaming with a difference of up to ~200 rows, and returns to `in_sync` with difference 0 once drained (`results/oncall/ws_capture_phase2.jsonl`).
- The drained check is count-based (live rows in Postgres vs live rows in Delta, minus quarantined keys that really exist in Postgres). It is weaker than `scripts/parity_checker.py`, which compares keys and values and stays the full proof; a value-only mismatch does not change counts.
- "Quarantined" must only subtract DLQ keys that are actual Postgres rows. First version subtracted every open DLQ key and the live badge read `mismatch (-1)` because the Phase-0 rogue `INVALID_UUID` message was never a Postgres row. replay-svc now returns `open_missing_keys` = open keys absent from the lake AND present in the source (`oncall/replay/source.py`).

## D-013 HTTP / API choices
- WebSocket library: `coder/websocket` (maintained, context-aware, `Ping` on its own connection). Behaviour learnt from the first test run: `CloseRead` closes the connection if the peer sends a data frame, the default read limit is 32 KiB, and closing a dead peer waits for its close handshake, so the ping-timeout path cancels the context instead of calling `Close`.
- `?access_token=` is accepted only on `/v1/live` (browsers cannot set headers on a WebSocket) and the access log records the path, never the query. REST routes reject query tokens (tested).
- `/metrics` is served on its own loopback port (8089), not the public router (tested to be 404 there).
- A PENDING replay is a 202 and its idempotency key is released so the same request can be retried to completion; every other definitive result (including 4xx) is stored and replayed. If the audit insert fails after the action ran, the handler logs `AUDIT WRITE FAILED` at error level and still answers (the replay already happened and is itself idempotent); a failed audit write is therefore loud but not fatal.
- `staticcheck` caught `chi/middleware.RealIP` (deprecated: spoofable X-Forwarded-For); removed. The API listens on loopback only and sits behind no proxy.

## D-014 OAuth / token choices
- **Backend-mediated flow with PKCE** exactly as the SPEC: the app sends an S256 challenge to `/v1/auth/github/start`, the server stores the state (hash only) with the challenge and redirect, GitHub redirects to the API callback, the API exchanges the GitHub code with its client secret and reads `/user` once (the GitHub access token is discarded), checks the allowlist (case-insensitive) and redirects to the app's deep link with a one-time code bound to the challenge. The app then posts `{code, code_verifier}` to `/v1/auth/token`. The secret never appears in a redirect or a response (tested: the mock records that it arrived server-to-server only).
- **Why PKCE if the server holds the secret:** the secret protects the API-to-GitHub leg; PKCE protects the last leg (API -> app). A deep link like `oncall://...?code=` can be claimed by another app on the phone; without the verifier that intercepted code is useless.
- A one-time code is **consumed before the verifier is compared**, so a wrong verifier burns the code (no brute force against one code). Codes live 2 minutes, states 10.
- `redirect_uri` is validated against an allow-list by scheme (custom schemes `oncall://`, `exp://`) or scheme + exact host for http(s) (`127.0.0.1`, `localhost`); lookalike hosts (`127.0.0.1.evil.example`), userinfo tricks and fragments are rejected (tested). A bad state never redirects anywhere.
- **Refresh tokens:** opaque 32-byte random values, stored only as SHA-256 hashes, rotated on every use inside one `SELECT ... FOR UPDATE` transaction. Presenting an already-rotated token revokes its whole family (the legitimate holder's newest token dies too) and is audited as `auth.refresh_reuse`; a token of an already-revoked family is `Revoked` and is not counted as a new reuse. Concurrency is tested against Postgres: 10 simultaneous refreshes of one token -> exactly 1 rotation. Allowlist membership and role are re-evaluated at every refresh, so removing or demoting a user takes effect within one access-token lifetime (15 min).
- Known limits (written down, not hidden): a stolen access token works until it expires (logout revokes the refresh family, not already-issued 15-minute JWTs); no rate limiting on `/v1/auth/*` (the API is loopback-only and reached through an SSH tunnel; add one before exposing it); the mock GitHub server proves the flow but not GitHub's real behaviour, which is Phase 6.
